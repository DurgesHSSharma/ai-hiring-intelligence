# Rules — AI Hiring Intelligence Platform

**Version:** 1.0
**Applies to:** every code-generation session on this repository.
**Read before writing code:** this file, then `Phases.md`, then `Memory.md`.

These rules are binding. Where a rule conflicts with a suggestion made mid-session, the rule wins unless the project owner overrides it explicitly.

---

## 1. Hard boundaries

### 1.1 Never touch the frontend

`frontend/` is authored and owned by the project owner.

- Do not create, edit, delete, rename, reformat, or lint any file inside `frontend/`.
- Do not change its styling, component structure, routing, state management, or dependencies.
- Do not "fix" its code, even when a bug is obvious. Report the bug in plain language and stop.
- Reading `frontend/` is allowed once it exists, and only for the purpose of matching the backend to it.
- When the frontend and backend disagree, the backend changes.

**Override (2026-09-06):** The project owner has explicitly directed this assistant to build `frontend/` directly in this repository, ahead of Phase 14's original "owner delivers it" precondition — see `Memory.md` decisions 89-90. This boundary is lifted for that purpose only. Every other rule in this file (no fabricated results, no secrets, layering discipline on the backend side, scope-of-change discipline, etc.) still applies in full to any frontend code written under this override.

### 1.2 Never run version control commands

No `git init`, `add`, `commit`, `push`, `pull`, `branch`, `merge`, `rebase`, `tag`, or remote operations. The owner handles all version control. Write files; do not stage them.

### 1.3 Never fabricate results

- No invented metric values. Precision, recall, F1, ROC-AUC, NDCG, and accuracy appear in documentation only after a real evaluation run produced them.
- Placeholders are written as `TBD — pending Phase N evaluation`, never as a plausible-looking number.
- No claim that something works without having run it.
- No fake screenshots, fake benchmark tables, or fake demo output.

### 1.4 Never commit secrets

- Real API keys, tokens, passwords, and connection strings never appear in any tracked file.
- `.env` is gitignored. `.env.example` carries keys with empty values.
- No secret in a notebook cell, docstring, test fixture, comment, or README.
- No secret in a log line, not even at debug level.

### 1.5 No attribution notices

The codebase and documentation contain no mention of how the code was produced — no generation notices, no tool credits, no "generated by" headers, no assistant names in comments, commit-style trailers, or docs. Write it as ordinary engineering work.

### 1.6 Stay inside the current phase

- Build only the phase named in `Memory.md` as current.
- Do not start the next phase because there is time left.
- Do not scaffold empty files for future phases.
- Spotting something worth doing later means recording it in the `Memory.md` backlog, not building it.

### 1.7 Scope of change

- Change the fewest files needed. A request to fix scoring does not license reorganising the API layer.
- Do not rename existing modules, functions, or database columns without being asked.
- Do not reformat files you did not otherwise need to modify.
- Do not upgrade or swap a dependency mid-phase.

### 1.8 Ask instead of guessing

Stop and ask when:

- A requirement in `PRD.md` is ambiguous in a way that changes the data model or the API contract.
- Two documents disagree.
- A phase seems to require a library not listed in §3.
- A dataset, model artefact, or credential is missing.
- The fix for a failing test would mean changing an intended behaviour.

One clear question beats an hour of work in the wrong direction.

## 2. Behaviour when writing code

### 2.1 Before

1. Read `Memory.md` to find the current phase and recent decisions.
2. Read the phase definition in `Phases.md` and note the acceptance criteria.
3. Read the files being changed. Do not rewrite a file from memory of what it probably contains.
4. State the plan briefly: files to create, files to change, why.

### 2.2 During

- Follow the layering in `Architecture.md` §2 exactly.
- Match the existing style of the file being edited.
- Write the smallest thing that satisfies the acceptance criteria.
- Add type hints on every function signature.
- Handle the failure path in the same commit as the happy path, not later.

### 2.3 After

1. Run the code. An unrun file is not finished.
2. Run the test suite. A phase with failing tests is not complete.
3. Update `Memory.md`: what was built, decisions made, deviations, what is next, anything broken.
4. Report honestly — including what was not finished and what is untested.

### 3.5 Forbidden without explicit approval

| Not used | Reason |
|---|---|
| Django, Flask, Litestar | FastAPI is the framework |
| Tortoise, Peewee, raw psycopg queries | SQLAlchemy is the ORM |
| LangChain, LlamaIndex, Haystack | One direct LLM call needs no orchestration framework |

| MongoDB, Firebase, Supabase client | PostgreSQL over SQLAlchemy |

### 3.6 Adding a dependency

Adding anything not listed above requires: naming the package, saying what it does that the approved set cannot, confirming it is maintained, and getting approval. Then pin it in `requirements.txt` with an exact version and note it in `Memory.md`.

### 3.7 Pinning

Every dependency is pinned to an exact version. No `>=` in `requirements.txt` except where a package genuinely requires a range. Two requirements files: `backend/requirements.txt` for runtime, `ml/requirements.txt` for training and notebooks. The API never depends on a notebook-only package.

## 4. Code standards

### 4.1 Python

- Python 3.11. Formatting: 4 spaces, 100-character soft line limit, double quotes.
- `snake_case` functions and variables, `PascalCase` classes, `UPPER_SNAKE` constants.
- Type hints on every function signature, including returns.
- Docstrings on public service and ML functions: what it does, what it returns, what it raises. Skip them on obvious one-liners.
- No wildcard imports. No relative imports beyond one level.
- No mutable default arguments.
- No business logic at module import time. Loading a model happens in the lifespan handler or behind a lazy singleton, never as a module-level side effect.

### 4.2 Layer discipline

| Layer | May import | Must not |
|---|---|---|
| `api/` | schemas, services, dependencies | models, ml, database sessions directly |
| `services/` | models, schemas, ml, utils, core | anything in `api/`, `HTTPException` |
| `ml/` | utils, stdlib, third-party ML | models, database, HTTP objects |
| `models/` | SQLAlchemy, base | services, api, ml |

A route body is: dependency injection, one service call, return. If a route grows an `if` about business rules, that logic belongs in a service.

### 4.3 FastAPI

- Every route declares a `response_model`.
- Every route declares an explicit `status_code` when it is not 200.
- Path parameters are typed. Query parameters use `Query()` with bounds where bounds exist.
- Routers are grouped by resource, prefixed, and tagged.
- Database sessions come only from the `get_db` dependency. No session is constructed inside a function body.
- Long CPU-bound work (embeddings, parsing) runs in `def` routes, not `async def`, so it does not block the event loop.

### 4.4 Pydantic

- Separate schemas per direction: `JobCreate`, `JobUpdate`, `JobResponse`. Never one model doing all three.
- `model_config = ConfigDict(from_attributes=True)` on response models.
- Validators live on the schema, not in the route.
- Enums are Python `Enum` classes shared between models and schemas. Never bare strings compared inline.
- `password_hash` never appears in any response schema. Not once.

### 4.5 SQLAlchemy

- Declarative models with `Mapped[...]` annotations.
- Explicit `nullable`, `index`, and `unique` on every column where it matters.
- Foreign keys always declare `ondelete` behaviour.
- No lazy-loading in a loop. Use `selectinload` or `joinedload` for related data.
- Filtering, sorting, and pagination happen in the query. Never fetch everything and slice in Python.
- Every schema change is an Alembic migration. No `Base.metadata.create_all` outside the initial bootstrap and tests.
- Never edit a migration that has already been applied. Write a new one.

### 4.6 ML code

- Inference functions are pure: data in, data out. No database, no filesystem writes, no HTTP.
- A model is loaded once and reused. Never loaded inside a request handler.
- Training happens only in `ml/`. The API never fits a model, not even a TF-IDF vectoriser on the fly — if a vectoriser is needed at request time, it is fitted per scoring run inside the service and discarded, and that is documented.
- Model, preprocessor, and feature-name list are always serialised and loaded together. A model without its feature order is unusable and must never be saved alone.
- Every random operation takes `random_state=42`.
- Every artefact carries a version string, surfaced through `/attrition/model-info`.

### 4.7 Prompts

- Prompt templates live in `app/ml/llm/prompts.py` as named constants. Never inline in a service function.
- Every prompt demands strict JSON with no prose and no code fences.
- Every LLM response is validated against a Pydantic schema before use. An unvalidated response is never persisted or returned.
- Prompt changes are recorded in `Memory.md` with the reason, because they change output quality invisibly.

### 4.8 Comments

Comments explain why, not what. Explain a non-obvious threshold, a workaround, a formula. Do not narrate code that already reads clearly. No commented-out code left behind. No `TODO` without a phase reference.

## 5. Error handling

### 5.1 Principles

1. Fail loudly at startup, gracefully at request time.
2. Never swallow an exception. No bare `except: pass`.
3. Never leak internals. A stack trace, SQL string, or filesystem path never reaches the client.
4. One partial failure never destroys a batch.
5. Every error message tells the user what happened and what to do next.

### 5.2 Exception hierarchy

Defined in `app/core/exceptions.py`:

```python
AppError(Exception)              # base — carries code, message, details, http_status
├── NotFoundError                # 404
├── ValidationError              # 400
├── ConflictError                # 409
├── AuthenticationError          # 401
├── AuthorizationError           # 403
├── FileValidationError          # 415 / 413
├── ParsingError                 # 422 — resume unreadable
├── ModelUnavailableError        # 503 — artefact missing or failed to load
└── LLMError                     # 503 — provider failure, timeout, invalid output
```

Services raise these. `error_handlers.py` maps them to the envelope in `Architecture.md` §6.1. `HTTPException` is not raised in service code.

### 5.3 Error codes

Stable, uppercase, snake. The frontend may switch on them, so they never change once shipped.

```text
JOB_NOT_FOUND              CANDIDATE_NOT_FOUND         SCORE_NOT_FOUND
APPLICATION_NOT_FOUND
DUPLICATE_EMAIL            INVALID_CREDENTIALS         TOKEN_EXPIRED
TOKEN_MISSING              TOKEN_INVALID               ADMIN_REQUIRED
UNSUPPORTED_FILE_TYPE      FILE_TOO_LARGE              BATCH_LIMIT_EXCEEDED
RESUME_PARSE_FAILED        RESUME_TEXT_TOO_SHORT       JOB_HAS_NO_SKILLS
NO_FILES_PROVIDED          CANDIDATE_NOT_APPLIED
SCORING_FAILED             EMBEDDING_MODEL_UNAVAILABLE
LLM_UNAVAILABLE            LLM_INVALID_OUTPUT          LLM_TIMEOUT
INTERVIEW_QUESTIONS_NOT_FOUND    INSUFFICIENT_GROUNDED_QUESTIONS
ATTRITION_MODEL_MISSING    INVALID_FEATURE_SET    EMPLOYEE_NOT_FOUND
INVALID_CANDIDATE_COUNT
RATE_LIMIT_EXCEEDED
INTERNAL_ERROR

REQUEST_VALIDATION_ERROR   VALIDATION_ERROR
NOT_FOUND                  METHOD_NOT_ALLOWED          HTTP_ERROR
```

`APPLICATION_NOT_FOUND` and `ADMIN_REQUIRED` were added in Phase 3 for `PATCH /applications/{id}` and the admin-only `DELETE /jobs/{id}` respectively (`AuthorizationError`'s existing 403 status, raised with this explicit code).

`NO_FILES_PROVIDED` was added in Phase 4 for `POST /jobs/{job_id}/resumes` — a request-level rejection (400, `ValidationError`) for a batch call with an empty file list, distinct from any per-file failure.

`CANDIDATE_NOT_APPLIED` was added in Phase 6 for `POST /jobs/{job_id}/score` — a per-candidate skip reason (in the 200 batch response, not a top-level error) when an explicitly-requested `candidate_id` has no `Application` to the job being scored.

`INTERVIEW_QUESTIONS_NOT_FOUND` was added in Phase 8 for `GET /candidates/{id}/interview-questions` (404, `NotFoundError`) — no questions have been generated yet for that candidate/job pair. Distinct from `LLM_UNAVAILABLE`/`LLM_INVALID_OUTPUT`/`LLM_TIMEOUT`, which are provider-call failures on `POST`, not "nothing stored yet" on `GET`.

`EMPLOYEE_NOT_FOUND` was added in Phase 11 (`NotFoundError`, 404) for `POST /attrition/predict`'s optional `employee_id` (persistence linkage — the id must reference a real `employees` row or the request is rejected before any prediction runs) — the `employees` table is a genuinely new resource type with no prior code covering "referenced row does not exist," distinct from every existing `*_NOT_FOUND` code.

`INSUFFICIENT_GROUNDED_QUESTIONS` was added in the Phase 8 grounding-filter fix (`LLMError`, 503) for `POST /candidates/{id}/interview-questions` — every generated question was parseable, valid JSON, and passed schema validation, but none of them referenced anything in the candidate's own extracted data. Deliberately distinct from `LLM_INVALID_OUTPUT`, which stays reserved for the model's raw output failing strict JSON parse or Pydantic validation even after one repair attempt: the two are different failures (a garbled response vs. a well-formed one the grounding filter rejected) and conflating them as one code hid, in a real run against real candidates, that the filter — not the model — was at fault. Between 1 and 4 grounded questions is no longer a failure at all; the response returns 200 with the shorter list and `partial: true` (`schemas/interview.py`), so this code fires only on a genuine zero.

`INVALID_CANDIDATE_COUNT` was added in Phase 12 (`ValidationError`, 400) for `GET /jobs/{id}/compare?candidate_ids=` — the same bounds-violation shape `BATCH_LIMIT_EXCEEDED` already covers for resume uploads, applied here to a 2–4 candidate count instead of a file count. Fires for a malformed `candidate_ids` value too (unparseable as a comma-separated integer list), since that is still "the count/shape of what was requested is not usable," not a distinct failure worth its own code.

`RATE_LIMIT_EXCEEDED` was added in Phase 15 (`RateLimitError`, 429) for `POST /candidates/{id}/interview-questions` — the only endpoint that spends an LLM call, and therefore the one place a runaway or hostile caller could drive real provider cost. A single in-process fixed-window counter, keyed per authenticated user id (`app/core/rate_limit.py`, wired via `app/dependencies.py::enforce_interview_generation_rate_limit`), rejects a user's request once they exceed `INTERVIEW_RATE_LIMIT_PER_HOUR` (default 20) within a rolling clock hour; `details.retry_after_seconds` tells the caller how long to wait. In-process rather than a shared store (Redis is forbidden — §3.5) because v1 runs as a single uvicorn process (Architecture.md §10); this stops being correct under multiple worker processes and would need revisiting first.

The second group are framework-level codes, not resource-specific ones: `REQUEST_VALIDATION_ERROR` is FastAPI's automatic Pydantic body/query validation (422); `VALIDATION_ERROR` is the default code on the base `ValidationError` `AppError` subclass before a service overrides it with something specific; `NOT_FOUND` / `METHOD_NOT_ALLOWED` / `HTTP_ERROR` come from Starlette's own routing exceptions (unmatched route, wrong method, anything else) rather than from application code.

### 5.4 Handling by category

**File upload.** Validate extension, then MIME type, then magic bytes, then size — in that order, cheapest first. Reject with a specific code. Store under a generated UUID name. Never trust the client filename for anything but display.

**Resume parsing.** Wrap extraction per file. On failure, record `parse_status = parse_failed` with a readable reason and continue the batch. Text under 100 characters is treated as a failure — a scanned image PDF must not become a candidate with an empty profile. Commit per file.

**Scoring.** A candidate with no extracted text is skipped with a reason, not scored as zero. A job with no required skills raises `JOB_HAS_NO_SKILLS` rather than silently scoring skill match at 100. Division guards on every ratio.

**LLM.** Timeout set explicitly. One retry on transient failure with a short backoff. Strict JSON parse; on parse failure, one repair attempt; on second failure, raise `LLM_INVALID_OUTPUT`. Never return prose as a question. Never let an LLM failure break the candidate detail response — question generation is a separate endpoint precisely so it can fail alone.

**ML inference.** Missing artefact at startup logs an error and disables only the attrition endpoints. A feature dict missing required keys raises `INVALID_FEATURE_SET` naming the missing keys. Probabilities are clamped to `[0, 1]`.

**Database.** Sessions always close via the dependency. Multi-write operations are wrapped in a transaction and rolled back on error. Integrity errors are caught and translated to `ConflictError` with a human message, not surfaced as a 500.

**Unhandled.** A catch-all handler logs the full traceback server-side with a correlation id and returns `INTERNAL_ERROR` with that id and nothing else.

### 5.5 Logging

- Structured logging via the stdlib `logging` module, configured in `core/logging.py`. No `print` in application code.
- Levels: `DEBUG` local detail, `INFO` lifecycle and request outcomes, `WARNING` recoverable degradation, `ERROR` failed operations, `CRITICAL` startup failure.
- Never log resume text, email addresses, passwords, tokens, or API keys. Log identifiers instead.
- Log every LLM call with model, latency, and outcome — never the full prompt or response body.

## 6. Testing

- `pytest`, tests mirroring the `app/` structure.
- Tests use an in-memory SQLite database created and torn down per test.
- No test hits a live LLM provider. The client is mocked at the boundary.
- Fixture resumes are small, committed PDF and DOCX files under `backend/tests/fixtures/`, containing invented people only.
- Every endpoint has at least one success test and one failure test.
- Every scoring formula has a unit test with hand-calculated expected values, including the worked example from the plan (85/90/80/100 → 87.5).
- Every phase adds tests for what it built. A phase without tests is not done.
- Deleting or weakening a test to make a suite pass is not allowed. Fix the code or report the conflict.

## 9. Product boundaries that hold no matter what

Some rules exist because the domain is hiring, and the cost of getting them wrong lands on real people.

- The system never auto-rejects, auto-advances, or emails a candidate.
- Every score is returned with its full breakdown. An endpoint that returns a bare number is not acceptable.
- Attrition output is a probability with contributing factors. It is never phrased as a statement about a person's intention or loyalty.
- Protected attributes are never model features, never scoring inputs, and never filter options.
- Limitations go in the README truthfully: dictionary-based skill extraction misses unlisted skills, ranking inherits bias from the text it reads, attrition models trained on one company's data do not transfer cleanly, and the LLM can misread a resume.
- Nothing in the codebase or documentation claims accuracy that has not been measured.
