**Phase 6 — TF-IDF ranking and composite fit score (this session):**

- `backend/app/ml/ranking/base.py` — the `Ranker` protocol: `fit(corpus: list[str]) -> None` plus `score(resume_text, job_text) -> float`. `score()` is exactly the signature `Architecture.md`'s folder-tree comment already documents; `fit()` was added to solve the TF-IDF corpus problem (see next bullet) without changing that documented shape. Phase 7's `EmbeddingRanker` drops in behind the same two methods with no `scoring_service.py` changes — `fit()` becomes a no-op (or where a batch job embedding gets computed), `score()` compares cached embeddings.
- `backend/app/ml/ranking/tfidf_ranker.py` — `TFIDFRanker`. `fit()` builds a **fresh** `sklearn.feature_extraction.text.TfidfVectorizer(stop_words="english")` per call, fit and held only for that instance's lifetime — never cached, never persisted (Rules.md §4.6: "fitted per scoring run inside the service and discarded, and that is documented" — this is that documentation). `score()` transforms both texts through the already-fitted vectoriser and returns `cosine_similarity × 100`. Verified directly (not assumed) that a zero-overlap pair resolves to `0.0`, never `NaN` or an exception — scikit-learn's `normalize()` step leaves an all-zero vector as zero rather than dividing by a zero norm.
- `backend/app/ml/ranking/factory.py` — `get_ranker(method: str | None = None)`. Returns `TFIDFRanker` for `"tfidf"`; raises `ModelUnavailableError(code="EMBEDDING_MODEL_UNAVAILABLE")` for `"embedding"`, since `config.py` already allows that value but Phase 7 hasn't built its ranker yet.
- `backend/app/ml/skills/skill_gap.py` — `compute_skill_gap(required_skills, candidate_skills) -> SkillGapResult` (matched/missing/additional/percentage, F6.1-F6.4). Pure, case-insensitive comparison — same convention `job_service.get_suggested_skills` already established. Single source of truth: both `scoring_service.py`'s `skill_match_score` and the `GET /candidates/{id}/skill-gap` endpoint read from the same stored result, no duplicate computation.
- `backend/app/services/scoring_service.py` — the core of the phase:
  - **`SCORE_VERSION = 1`**, a hand-maintained module constant. Bumped by a person when the scoring *formula* itself changes (a new sub-score, Phase 7's embedding method) — never bumped automatically when a `.env` weight is retuned, since that's normal operation within the same formula version.
  - **`_compose_final_score()`** — F7.1's weighted sum, extracted as its own pure function specifically so the worked example (85/90/80/100 → 87.5, Rules.md §6) could be unit-tested directly rather than reverse-engineered through TF-IDF's non-deterministic output. Drops any `None` sub-score and renormalizes the remaining weights to sum to 1.0 — resume_match and skill_match are never `None`, so `weight_sum` is always > 0.
  - **`_experience_score()`** — `min(years/required, 1.0)×100`. `required_years <= 0` → `100.0` (trivially met, a defined case not a division error). `years is None` → `None` (unknown, not zero).
  - **`_education_score()`** — ordinal ladder, 100/70/40. `candidate_level is None` **or** `required_level is None` (the job's own requirement text didn't resolve to any ladder level) → `None` in both directions, excluded from the composite rather than guessed either way.
  - **`_select_candidates()`** — explicit `candidate_ids` (each must have an `Application` to the job, else skipped with the new `CANDIDATE_NOT_APPLIED` code) always wins over `force`; otherwise `force=true` scores every applied candidate unconditionally, and the default scores only candidates with no existing score **or** an existing score flagged `is_stale` — a scored, non-stale candidate is left untouched. Reading "unscored" to include stale rows (Architecture.md 7.2 says only "unscored") was a judgment call: without it, a stale flag would never clear short of a full `force` rescore, defeating F7.7's whole point.

**Phase 7 — embedding upgrade (this session):**

- `backend/app/ml/ranking/embedding_ranker.py` — `EmbeddingRanker`, implementing the same `Ranker` protocol (`fit`/`score`) TF-IDF already uses.
  - `_get_model()` — a **module-level** `lru_cache(maxsize=1)`, not an instance attribute: every `EmbeddingRanker` across every request shares the one loaded model, satisfying Rules.md 4.6's "loaded once, never per request" at the process level, not just per-instance. Lazy, not eager in `main.py`'s lifespan — the shipped default is `SCORING_METHOD=tfidf`, so an install that never switches to embedding mode never pays for the ~90MB download or the (slower) `sentence_transformers`/`torch` import at all. Confirmed live: the import+load together took ~10-25s on first real use (network + CPU), well under any request timeout, and app startup itself is completely unaffected regardless of model availability (no lifespan change).
  - `sentence_transformers` is imported **inside** `_get_model()`, not at module level — deliberately, so the heavy `torch`/`transformers` import itself (not just the model weights) is deferred until first actual use, not paid at every app startup even under `tfidf` mode.
  - Model download path: confirmed live at `C:\Users\<user>\.cache\huggingface\hub` (via `huggingface_hub`, the actual backend `sentence-transformers` 3.3.1 uses) — entirely outside the project tree, so nothing needed adding to `.gitignore`. On first run with nothing cached, the underlying `SentenceTransformer(...)` construction reaches out over the network; any failure there (no network, corrupted cache, bad model name) is caught and re-raised as `ModelUnavailableError(code="EMBEDDING_MODEL_UNAVAILABLE")` — `functools.lru_cache` does not cache exceptions, so a later call retries rather than being stuck on a stale failure.
  - `self._cache: dict[text, vector]` is instance-level (dies with the ranker/request) — this is what makes `fit()` a real batch precompute: it embeds every not-yet-cached string in the given corpus in **one** `SentenceTransformer.encode()` call, not one call per candidate, and `score()` then looks both texts up by exact match instead of re-embedding. Verified directly with a mocked encoder counting calls: `fit()` on a 3-document corpus makes exactly 1 `encode()` call.
  - `seed(text, vector)`/`embed(text)` — two small methods beyond the minimal `Ranker` protocol surface (Protocols are structural; `TFIDFRanker` simply doesn't have them). `seed()` is how `scoring_service.py` injects an already-persisted `candidates.embedding` vector before `fit()` runs, so it's never re-encoded; `embed()` is compute-or-return-cached for one string, used both internally by `score()` and by `scoring_service.py` to persist a freshly computed vector after scoring.
  - `score()` scales cosine similarity to `[0, 100]` and **clamps** it (`max(0.0, min(100.0, ...))`) — unlike TF-IDF's non-negative term-count vectors, sentence embeddings can in principle produce a negative cosine similarity, which would otherwise render as an out-of-range sub-score.
- `backend/app/ml/ranking/factory.py` — `get_ranker("embedding")` now returns `EmbeddingRanker()` unconditionally. Construction never touches the model (no I/O in `__init__`), so a broken/missing model surfaces later, at the first real `fit()`/`score()` call, not at ranker-selection time.
- `backend/app/services/scoring_service.py`:
  - `_warm_embedding_cache(ranker, candidates)` — before `ranker.fit(corpus)` runs, seeds any already-persisted `candidate.embedding` into the ranker's cache via `seed()`. Duck-typed (`hasattr(ranker, "seed")`), not an isinstance check, so this is a genuine no-op for `TFIDFRanker` without this module needing to import `embedding_ranker.py` at all — confirmed the `tfidf` path executes byte-identical code to Phase 6 by re-running all of Phase 6's original scoring tests unmodified (see below).
  - `_score_one_candidate()` — after `ranker.score(...)`, if the ranker exposes `embed()` (embedding mode only) and `candidate.embedding` is still `None`, computes and persists it (`candidate.embedding = ranker.embed(candidate.resume_text)`) — this is a cache lookup at that point, not a second encode call, since `fit()` already embedded it. Committed in the same `db.commit()` that already happens per candidate in `score_job()`'s loop, so no new transaction was added.
  - **Model-load failure surfaces as a loud, whole-call 503, not a per-candidate skip** — deliberately. `ranker.fit(corpus)` in `score_job()` already ran *before* the per-candidate `try/except` even in Phase 6's original code; a `ModelUnavailableError` raised there propagates straight through to `error_handlers.py`'s existing `AppError` handler with **zero new guard code**. This means: with `SCORING_METHOD=embedding` and a broken model, `POST /jobs/{id}/score` returns 503 `EMBEDDING_MODEL_UNAVAILABLE` and writes no `CandidateScore` rows at all for that call; with `SCORING_METHOD=tfidf` (the shipped default), the embedding model is never reached regardless of whether it works, confirmed by running the tfidf path with the model fixture forced to raise on every call.

Checked **once per `score_job()` call**, not once per candidate: `functools.lru_cache` doesn't cache a failed load, so a per-candidate check would re-attempt (and re-fail, and re-log) the same load up to once per candidate in the batch. **Phase 7 — follow-up (this session, second round): threshold reclassified as blocking, band-calibration finding formally recorded.** The project owner reviewed the comparison and the semantic-threshold sanity check and gave two corrections plus one piece of process feedback, all incorporated before Phase 8:

1. **The threshold isn't just untuned — it's inverted on the cases that matter, and that's worse than no semantic matching at all.** `"PostgreSQL"`/`"MySQL"` (two different database products) passes at 0.547 while `"AWS"`/`"cloud infrastructure"` (a genuine paraphrase) fails at 0.492 — a candidate gets credited for the wrong product while a real synonym gets nothing. Per the project owner's explicit instruction: no tuning attempt (still no labelled set to tune against), and the feature must **refuse to run**, not merely warn per use. Implemented as a two-layer gate: `app/config.py` logs one startup `WARNING` (not a startup failure — the operator opted in on purpose, they just need to know it currently has no effect) whenever `SEMANTIC_SKILL_MATCHING=true`; `app/ml/skills/skill_gap.py` gained a hardcoded `THRESHOLD_VALIDATED = False` constant, checked in `scoring_service._semantic_embed_fn()` **before** `settings.SEMANTIC_SKILL_MATCHING` is even allowed to matter — the feature is inert regardless of the config flag until a person validates a real threshold and flips this constant, not until an operator flips a config value. `Phases.md`'s Phase 13 line was rewritten from "tune" to "must be validated... before the feature is enabled in any real use." `docs/EVALUATION.md`'s section was retitled from "sanity check, not evidence" to "BLOCKING ISSUE, not merely unvalidated," with the false-positive risk (crediting the wrong product) stated as the reason it's blocking, not just the false negatives. See decision 46 below.
2. **The `band`/`SCORING_METHOD` finding was under-stated as a "known limitation" — it's a direct recruiter-facing consequence.** Recorded explicitly, here and in `docs/EVALUATION.md`: PRD F7.5's band thresholds were set as fixed values against no particular scoring method, calibrated for neither TF-IDF's nor embedding's actual score distribution — and the comparison run proved they don't happen to suit both (same 12 resumes, same job: `weak_match` under one method, `moderate_match` under the other for the top 3). `band` is the field a recruiter actually acts on, so this is the two scoring methods disagreeing about who's worth a look, not a cosmetic scaling difference. `Phases.md`'s Phase 13 build list gained its own line: "Calibrate score band thresholds against the labelled ranking set, per scoring method."
3. No code change — feedback on process: correcting the project owner's own "~10 shape-change tests" estimate down to the real count (3), with diffs shown, rather than padding the change list to match the stated number, was called out as the right instinct.

## Decisions made and why

*(Phase 2's decisions 1–5 and 7 stand as originally recorded — see git history / prior notes. Decision 6 below is corrected, not merely superseded, because it described the exact hole Fix 1 closed.)*

6. ~~`UserCreate` accepts an optional `role`, defaulting to `recruiter`.~~ **Corrected this session.** This was wrong: nothing in `PRD.md`/`Phases.md` asked for a client-settable role, `Rules.md` §1.6/1.7 forbid adding scope unprompted, and — critically — `POST /auth/register` is public and unauthenticated, so this was a live privilege-escalation path the moment any role-gated endpoint existed (which Phase 3 introduced: admin-only job delete). Fixed by removing the field entirely and hardcoding `recruiter` in `auth_service.register()`. See Fix 1 above.
8. **`UserCreate` uses `extra="forbid"`, not Pydantic's default `extra="ignore"`.** Project owner's explicit correction during plan review: silently dropping an unrecognised field like `role` gives no signal anything was wrong — a later refactor or a frontend that starts sending it would fail silently forever. Rejecting it outright (422) mirrors `config.py`'s `Settings`, which already uses `extra="forbid"` for the same reason.
9. **`GET /jobs` status filter is `open` (default) / `closed` / `all`, not just the two real `JobStatus` values.** Project owner's explicit correction: PRD F2.5 ("close hides it from the default list") justifies defaulting to open, but without an `all` option, closed jobs would be reachable only by guessing the parameter exists, and there'd be no way to list every job. `"all"` is a query-only filter sentinel, not a third `JobStatus` enum member — the domain enum stays exactly `open`/`closed`.
10. **`passive_deletes=True` added to every one-to-many relationship on `Job`, `Candidate`, and `Employee`** (`applications`, `candidate_scores`, `interview_questions` on `Job`; the same three plus `candidate_skills` on `Candidate`; `attrition_predictions` on `Employee`, added as a follow-up once the same gap was confirmed there too). **Not in the original plan — discovered empirically while building the delete-cascade test the project owner asked for.** The plan's assumption ("no ORM-level cascade configured, so cascading is DB-level only, identical whether the delete happens through the ORM or raw SQL") was wrong: SQLAlchemy's default relationship behavior, even with no `cascade=` set, still loads a parent's related collections on delete and tries to NULL their foreign keys itself *before* issuing the DELETE — which fails outright against `NOT NULL` FK columns like `applications.job_id`, and never even reaches the database's own `ondelete="CASCADE"`. `passive_deletes=True` tells the ORM to trust the database's cascade instead of managing it itself. No schema/migration change — this is purely `Session`-level flush behavior. This is exactly the kind of bug the project owner's insistence on an empirical cascade test (rather than trusting a read of the model file) was designed to catch, and it did — twice, once for Job/Candidate and once more for Employee, confirmed both times by watching the same test fail without the fix before trusting it passing with the fix.
11. **DELETE responses are `200` with `{"id", "deleted": true}`, not `204`.** `Architecture.md` §6.3's status-code table enumerates every code actually in use and doesn't include 204.
12. **`APPLICATION_NOT_FOUND` and `ADMIN_REQUIRED` added to `Rules.md` §5.3** — the code table had no code for a missing application, and none for the new admin-only-action case.
13. **Candidate list stays pagination-only in Phase 3** — `Architecture.md` §6.2 shows a fuller `/candidates` query surface (`job_id`, `min_score`, `skills`, etc.), but that's PRD F12, explicitly scheduled for Phase 12. Building it now would be starting a later phase early.
14. **`PATCH /applications/{id}` lives in `api/candidates.py`/`candidate_service.py`**, not its own module — `Architecture.md` §3's folder tree has no `api/applications.py`, and groups the endpoint under the "Candidates" table section.
15. **Candidate delete does no file handling.** `Architecture.md`'s endpoint table says delete removes "candidate and file," but Phase 3 explicitly excludes file handling of any kind, and no upload endpoint exists until Phase 4. This phase deletes the DB row only. *(Superseded in Phase 4 — see decision 23: delete now removes the stored file too, as originally documented.)*
16. **Validation failures never create a candidate row; parse failures always do.** Project owner's explicit correction to the Phase 4 plan. A Tier-1 failure (extension/MIME/magic-bytes/size) means the upload was never a resume — no row, no file stored. A Tier-2 failure (extraction threw, or cleaned text is under 100 characters) means a real file was accepted and stored but couldn't be turned into usable text — PRD F3.7 requires this to still create a candidate row with `parse_status=PARSE_FAILED` and a readable `parse_error`, "not silently dropped," and the file is kept so the recruiter can open it and see why. `Architecture.md` §6.2's example response (a failed entry with no `candidate_id`) was the outlier here, not the rule — it's only accurate for a Tier-1 failure.
17. **Top-level HTTP errors are request-level only; every file-level failure (all four validation tiers, plus both parse failure modes) is embedded per-file in a 200 batch response.** Project owner's explicit correction — a single bad file must never block an otherwise-good batch, and the endpoint needs one predictable code path rather than a batch's status depending on how many files happened to fail. Only three checks abort the whole call, all before the per-file loop even starts: job not found (404 `JOB_NOT_FOUND`), empty file list (400 `NO_FILES_PROVIDED`), batch over `MAX_FILES_PER_BATCH` (400 `BATCH_LIMIT_EXCEEDED`). This meant amending `Phases.md`'s Phase 4 acceptance line, which was written assuming a single-file endpoint (see `Phases.md`'s current wording, and the file list above). The literal 415/413 pairing (`Rules.md` 5.2's `FileValidationError # 415 / 413`) is proven at the validator level instead — `validate_and_read_upload` genuinely raises with those statuses, verified by running the exact exception through the real `error_handlers.py` code.
18. **`candidates.email` made nullable (migration `ab794d7756c3`).** Project owner's explicit approval (Flag 2). Email extraction is regex work that belongs to Phase 5's `field_extractor.py`, and Phase 4 has no mechanism to populate it — inventing a placeholder would corrupt Phase 5's dedupe-by-email logic worse than a placeholder name would corrupt Phase 5's accuracy measurement. No `unique` constraint exists on the column, so multiple `NULL`s are schema-safe. **Carry-forward for Phase 5: dedupe-by-email must explicitly skip rows where `email IS NULL` — every Phase-4 candidate has a `NULL` email, and without an explicit skip they'd all collapse into a single dedupe match.**
19. **`files: list[UploadFile] = File(default_factory=list)`, not `File(...)`.** Discovered empirically, not assumed: a required `File(...)` field makes FastAPI reject a wholly-absent multipart part with its own `REQUEST_VALIDATION_ERROR` (422) before the route function ever runs, which would make the service layer's `NO_FILES_PROVIDED` check permanently unreachable. `default_factory=list` lets an absent field arrive as `files=[]` instead, so the service's own check — and its more specific 400 code — actually fires. Verified both ways via a direct `TestClient` call before and after the change.
20. **DOCX magic-byte validation checks for `word/document.xml` inside the archive, not just the `PK\x03\x04` ZIP signature.** That signature alone is shared by `.xlsx`, `.pptx`, `.jar`, and any renamed `.zip`; only the presence of `word/document.xml` (an `.xlsx` has `xl/` there instead, a `.pptx` has `ppt/`) actually confirms a Word package. Uses stdlib `zipfile`, reads only the central directory, no decompression needed.
21. **Header/footer stripping is PDF-only** — `python-docx`'s `.paragraphs` never includes header/footer content in the first place (it lives in separate `section.header`/`section.footer` XML parts), so DOCX structurally never needs the step. For PDF, three independent guards (edge position within 2 lines of a page boundary, repetition across most pages, ≤100 characters) keep it from ever touching real content, even content that happens to repeat.
22. **Test fixtures were hand-built directly against the PDF spec, using no library beyond the stdlib, rather than adding a PDF-writing dependency.** `matplotlib` is Rules-approved for `ml/` (§3.2) and could write PDFs, but it isn't installed in the shared `backend/.venv` and isn't in `backend/requirements.txt` — per `Rules.md` §3.7 it belongs in `ml/requirements.txt` only, and adding it to backend just for offline fixture generation would create an undeclared runtime dependency mismatch. `python-docx` (already a real, installed backend dependency) writes the DOCX fixture directly.
23. **`DELETE /candidates/{id}` now deletes the stored file too, and `GET /candidates/{id}/resume-file` streams it** — both deferred from Phase 3 (decision 15) since no upload endpoint existed yet. File deletion happens *after* the DB commit succeeds, never before: if file-deletion-first were interrupted by a failed commit, a live candidate row would point at a missing file, which is worse than the reverse (an orphaned file with no row, already harmless and gitignored). `get_resume_file` in the service layer returns a plain dataclass, not a `FileResponse` — `Rules.md` 4.2 forbids services/ from touching HTTP response classes, so the actual `FileResponse` (explicit `media_type`, `filename=resume_filename` for the download name) is built in `api/candidates.py`.
24. **Test file storage isolated via a `upload_dir` fixture (`monkeypatch` + `tmp_path`), wired into `client` the same way `db_session` already is.** Project owner's explicit instruction, flagged as "the same class of bug the in-memory DB fixture already solves." Confirmed empirically: `backend/storage/` had 0 files before a full suite run and 0 after.
25. **DOCX extraction now walks `document.element.body` in true document order (paragraphs and tables interleaved), instead of `document.paragraphs` alone.** Project owner's explicit instruction, prioritized above the PDF column work as "the more serious of the two bugs" — a table-based sidebar (a common way to fake a 2-column layout in Word) was previously invisible to extraction with no error anywhere: silent data loss, not visible scrambling, meaning a real candidate's entire skills column could vanish and produce a plausible-looking low score with nothing in any log to explain why. Proven with `two_column_table_resume.docx`: the old path sees 5 lines total (the table's content — the entire sidebar — simply isn't there); the new path sees all of it, correctly ordered relative to the paragraphs before and after the table. Table content is read row-then-cell, which is exactly correct for a single-row, two-cell table (the common case for a faked sidebar) but would not fully reorder a *multi-row* column-layout table into two continuous reading streams — noted as a narrower residual limitation, not fixed here, since it wasn't what was asked for and no real sample exhibiting it has been seen.
26. **PDF column-splitting was NOT implemented — investigated, blocked on evidence, and reported rather than guessed.** Project owner's explicit instruction: build the dates-column adversarial fixture (single-column, right-aligned dates — `"Senior Data Engineer, Acme Corp{pad}2021 - Present"`, 8 such lines) *before* choosing a threshold, measure its gutter confidence, and "if the two overlap, stop and tell me rather than picking a threshold that splits the difference." Measured, using a word-position row-gap-fraction scan (`page.extract_words()` grouped into row-bands, scored by what fraction of rows spanning a candidate x actually have a gap there): `real_resume.pdf` p.1's genuine 2-column gutter scores **100% confidence over 6 rows**; the dates-column fixture (Courier/monospace) scores **90% confidence over 10 rows**. A 10-point gap on two single real/synthetic samples is not "clearly above / clearly below" by any reasonable reading, so no threshold was chosen and no crop-and-split logic was wired into `text_extractor.py` — `_extract_pdf_text` is byte-for-byte the original Phase 4 code, proven by the new `test_pdf_extraction_output_pinned_exactly` regression pin. While investigating *why* the two collide, found one promising secondary signal, not yet validated enough to trust: counting rows with content on the *right side of the gutter only* (no corresponding left-side content on that row) cleanly separates the two extreme cases (`real_resume.pdf` p.1: 29 right-only rows, out of 63 total — a real sidebar has its own independent flow of lines; the dates fixture: 0 right-only rows, by construction, since every date is attached to a title on the same line) — but the same check on the *other* fixtures was noisier than that clean pair suggested (`real_resume.pdf` p.2's already-rejected weak candidate: 4 right-only rows despite no real column there; `sample_resume.pdf`'s coincidental best candidate: 8 right-only rows despite being genuinely single-column), so this is a lead worth the project owner's consideration, not a validated fix.
27. **PDF column-splitting formally deferred to Phase 13, not left as an open question.** Project owner's instruction, in two parts. First: re-measure the dates fixture in a proportional font (Helvetica, positioned via absolute `Tm` per run so the date column sits at a real fixed x despite each title's different rendered width), since Courier's perfectly-uniform padding was suspected worst-case rather than representative. It wasn't — confidence came back at **100% over 9 rows**, if anything stronger than Courier's 90%/6. The reason: a fixed-position date column always leaves some sub-region between the widest title's end and the date's start that reads as empty on every dated row, and a point-based gap scan finds exactly that core empty zone regardless of how ragged the rest of the gap is — raggedness doesn't defeat this signal the way it might have been expected to. Second, given that result: defer to Phase 13 rather than keep iterating on two synthetic samples, on the project owner's own reasoning — tuning a threshold against two synthetic fixtures is guessing, whereas Phase 5 builds a labelled set of 30 real-format resumes to measure extraction accuracy against, which is the actual corpus this decision needs (any resume where Phase 5 extraction underperforms becomes a sample to inspect for column corruption), and Phase 13 formally evaluates extraction quality — the right place to revisit this with evidence instead of two hand-built adversarial cases. `Phases.md`'s Phase 13 build list now carries its own line for this, so it isn't only a `Memory.md` note that could get missed.

28. **Two labelled evaluation sets, not one — a project-owner correction to the original Phase 5 plan.** The original plan proposed building all 30 evaluation resumes synthetically (structured data → generated PDF/DOCX → labels computed from that same structured data) and measuring PRD F3.5 accuracy against them. Project owner's explicit objection: this is a closed loop — the generator and the extractor share the same assumptions about date formats, heading vocabulary, and phrasing, so the extractor is only ever tested on variation its own author thought to build in. This is exactly the trap `real_resume.pdf` (Phase 4) already exposed at the text-extraction layer, now one layer up. A number produced this way, once it lands in `docs/EVALUATION.md` and eventually the README, would look like a measurement without being one — "worse than having no number" (project owner's words). Split instead: the 30 synthetic resumes stay as `regression_eval_set/`, a regression suite whose numbers never represent accuracy and never reach `docs/EVALUATION.md`; the real PRD F3.5 numbers come only from `real_eval_set/`, 10-15 real-template resumes the project owner is producing and hand-labelling independently, specifically so the ground truth has no dependency on anything this codebase generated. `scripts/evaluate_field_extraction.py` refuses to run against the regression suite at all (explicit check, explanatory message) rather than relying on a human never pointing it at the wrong directory by mistake.
29. **`GET /jobs/{id}/suggested-skills` is read-only; `job_service.create_job`/`update_job` are unchanged from Phase 3 — a project-owner correction to the original Phase 5 plan.** The original plan auto-unioned skills extracted from the job description into `required_skills` on create/update, reading PRD F4.5 ("the recruiter does not have to list every skill by hand") as license to write automatically. Project owner's explicit objection: silent mutation means the recruiter can't tell what they typed from what was inferred, can't remove an inferred skill (it reappears the next time the description is edited and extraction reruns), and required_skills changing without recruiter action interferes with Phase 3's own stale-marking logic (`update_job`'s `marks_stale` check compares `required_skills` by value). The corrected design serves F4.5 without any of that: the recruiter sees suggestions and adds what they want through the PATCH endpoint that already exists.
30. **Every post-measurement fix required its own one-line "why this generalizes beyond these 12 files" justification, and a fix without one wasn't made.** Project owner's explicit instruction for the fix round following the real evaluation measurement. Concretely: four vocabulary additions were made (each defensible as standard, widely-used terminology, not corpus-specific phrasing) and one was explicitly declined (`"Diploma di Maturita"` — could not be defended as anything but a one-off patch for `resume_011`, since real multi-language support is a scoping decision, not a quick addition) even though making it would have "fixed" that resume's score. This is the same discipline as decision 28's two-eval-set split, applied one level down: a fix that only works because it was shaped around the test data is a different thing from a fix that happens to also help the test data, and only the second kind gets made.

31. **The `Ranker` protocol is `fit(corpus)` + `score(resume, jd)`, not just `score()` alone.** `Architecture.md`'s folder-tree comment documents only `score(resume, jd) -> float`. Fitting a TF-IDF vectoriser on just the one resume/job-description pair being compared would make IDF nearly meaningless (every term is either "in both documents" or "in one," no real rarity signal) — flagged to the project owner before building, per Rules.md §1.8 ("two documents disagree": the documented single-method interface vs. Rules.md §4.6's requirement that a per-request-fitted vectoriser still be a real one). **Known limitation — two-column PDF resumes (deferred to Phase 13, decision 27; do not lose this):**

- Two-column PDF resumes interleave columns on extraction. Confirmed and reproducible with `real_resume.pdf` page 1.
- The right-only-row signal (29 vs. 0) is the most promising discriminator and is structurally motivated: a dates column has content on both sides of the gutter on every row, while a true sidebar has many single-sided rows because the columns flow independently. Start there when this is revisited.
- Gutter-gap confidence alone does NOT discriminate: dates fixture 90% (Courier) / 100% (Helvetica, proportional), real two-column 100%. Font proportionality does not rescue this signal — verified, not assumed.
- **Evidence from Phase 5's regression suite (synthetic), now corroborated on the real 12-resume corpus too:** two-column PDF corruption does not fail every field uniformly. Email and phone extracted correctly on all 4 two-column resumes in the real set. Name, education, and experience-years were the fields actually hit — and on the real corpus, the mechanism turned out narrower than the regression suite alone suggested: it's specifically **heading-line corruption** (a two-column layout welding `EXPERIENCE` or `CONTACT` onto an adjacent line) that breaks section-scoping and cascades into an experience-years overcount, not direct corruption of the date/email/phone data itself. The regression suite's name-welding case (`"Harper Quinn CONTACT"`) and the real corpus's heading-welding cases (`"Wei Chen EXPERIENCE"`, `"CONTACT EXPERIENCE"`) are the same underlying phenomenon (`pdfplumber`'s y-position text join) hitting different lines depending on what happens to sit next to what in the layout.
- **The real corpus also surfaced that this same fallback path breaks on plain single-column resumes for an unrelated reason** — `resume_007`'s `"APPOINTMENTS"` heading wasn't on the recognized vocabulary list, no column corruption involved, and produced the largest single overcount in the set (21.0 vs. 11.0 years). This one is now **fixed** (`"appointments"`/`"positions"`/`"career history"` added) — confirms "recognized heading vocabulary is incomplete" and "two-column heading corruption" really were two separate problems, since fixing the vocabulary gap did nothing for the two-column cases and vice versa.
- **Final, corrected count after the fix round: exactly 3 two-column resumes have any miss, but only 2 of them (`resume_003`, `resume_008`) are actually caused by heading-line corruption.** `resume_003` misses name + experience-years (`"Wei Chen EXPERIENCE"`); `resume_008` misses experience-years (`"CONTACT EXPERIENCE"`) — both confirmed via traced month-index arithmetic to be section-scoping failures, not interval-merge defects (the merge logic correctly preserved `resume_008`'s real 30-month gap; the overcount came entirely from an EDUCATION date that shouldn't have been a candidate interval at all). **`resume_003` and `resume_008` are the actual Phase 13 carry-over for this specific mechanism.** `resume_011` also has a miss (education) and is also two-column, but its cause is the deliberately-unfixed non-English vocabulary gap (`"Diploma di Maturita"`), unrelated to heading corruption — its EXPERIENCE and EDUCATION sections were both located correctly. Don't let "three two-column resumes had misses" become "three instances of column corruption" — only two are.
